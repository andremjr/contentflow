## Resultado observável

O contrato do pacote agora documenta e testa o fluxo:

```text
BUSCAR candidatos externos
  → VALIDAR candidatos produzidos nesta execução
  → CRIAR artifacts locais materializados
```

`ESCOLHER` é rejeitado conceitualmente porque seleciona somente itens preexistentes da Biblioteca Estratégica. A validação dos candidatos stock pertence ao núcleo e ao Método; não foi criada uma capability de plugin para substituir o bloco universal `VALIDAR`.

A porta `selected_assets` foi preservada por compatibilidade. Na capability `search-stock-by-briefs`, ela representa uma sugestão de descoberta ranqueada (`automatic_best`) ainda pendente de validação editorial. O nome legado não concede estado de aprovação ao record.

## Schema canônico do candidato

A fixture reproduzível está em `ecosystem/plugins/reference/free-stock-media-studio/fixtures/p20-contract.json`.

Campos obrigatórios de qualquer candidato:

| Campo                         | Semântica                                            |
| ----------------------------- | ---------------------------------------------------- |
| `asset_id`                    | identidade composta estável do provedor e ID externo |
| `external_id`                 | identidade original no provedor                      |
| `provider`, `provider_label`  | origem técnica e nome legível                        |
| `media_type`                  | `image` ou `video`                                   |
| `preview_url`                 | prévia remota para inspeção antes do download        |
| `source_url`                  | página pública original do item                      |
| `attribution`                 | texto de crédito preservado                          |
| `license_name`, `license_url` | licença declarada e sua referência                   |

Materialização exige pelo menos uma entre `download_url` e `download_location`. Sugestões por briefing também carregam `brief_id`, tempos, `query_used`, `candidate_score` e `selection_mode`. Dimensões, duração, MIME, autor, tamanho e diagnóstico de busca permanecem no record quando conhecidos.

## Schema canônico do artifact

Campos universais obrigatórios:

| Campo      | Semântica                                 |
| ---------- | ----------------------------------------- |
| `id`       | ID local determinístico da tentativa/item |
| `name`     | nome relativo dentro da saída autorizada  |
| `mimeType` | MIME verificado pelo conteúdo             |
| `size`     | bytes realmente gravados                  |
| `url`      | referência local `artifact://...`         |

No download por briefing, o record de arquivo também preserva `brief_id`, tempos, provider, página de origem, atribuição e licença. Downloads singulares entregam a mesma proveniência pela porta separada `provenance`.

## Comportamentos caracterizados

- **Falha parcial:** uma fonte bem-sucedida mantém seus resultados quando as outras cinco fontes de imagem falham; cada falha produz warning por provedor.
- **Deduplicação:** o mesmo provider/ID/tipo aparece uma vez, preservando o candidato de maior score; IDs iguais de providers diferentes não colidem.
- **Licença:** `commercial_safe` rejeita `BY-NC` e `BY-ND` e mantém licença comercial declarada.
- **Tracking:** duas execuções idênticas de download Unsplash materializam o arquivo, mas registram o evento obrigatório apenas uma vez para a mesma tentativa lógica.
- **Redirect:** redirect entre hosts oficiais do mesmo provedor é aceito; salto para host externo é recusado com `PERMISSION_DENIED`.
- **MIME:** header `image/png` com assinatura inválida é recusado e não se torna artifact.
- **Proveniência:** os schemas canônicos exigem origem/licença antes e depois da materialização.
