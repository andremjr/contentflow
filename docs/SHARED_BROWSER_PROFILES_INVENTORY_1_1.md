# Pacote 1.1 — inventário de perfis de navegador

Data do levantamento: 2026-09-26. Branch observada: `main`.

Este documento registra o estado existente antes da migração para perfis globais. Ele é descritivo: não altera fonte de verdade, schema, runtime, UI nem formato portátil.

## Resumo do modelo atual

- `plugin_profiles` é a fonte persistida do inventário de perfis e pertence diretamente a `plugin_id`.
- O alias é único somente dentro do plugin (`plugin_id + alias COLLATE NOCASE`).
- Métodos persistem o alias principal e, quando declarado, os aliases de fallback dentro de `block.plugin.configuration` usando `profileSetup.configurationKey` e `fallbackConfigurationKey`.
- `profileInventory()` também reconstrói registros ausentes a partir dos Métodos existentes por `syncPluginProfilesFromMethods()`.
- O workspace customizado é persistido por plugin em `plugin_workspaces`. Quando ele existe, substitui o workspace padrão inclusive para plugins com `profileSetup`.
- Sem workspace customizado, plugins com `profileSetup` recebem `%APPDATA%/ContentFlow/data/plugin-workspaces/profiles/<plugin-id-sanitizado>` como workspace estável. Outros plugins recebem, por execução, `plugin-workspaces/<project-id>/<plugin-id>`.
- `services.getWorkspacePath()` é hoje usado ao mesmo tempo para estado privado/checkpoints e para a pasta física do Chrome. Essa mistura é a principal fronteira que a fase 4 deverá separar com `getProfilePath()`.

## Fluxos observáveis que dependem de alias

1. **Cadastro/descoberta:** a Central chama `GET /profiles`; `profileInventory()` sincroniza aliases encontrados em Métodos e devolve usos.
2. **Edição de Método:** `ManagedProfileSelector` grava o alias principal e os fallbacks em texto dentro de `block.plugin.configuration`.
3. **Builder MCP:** `builderPluginContexts()` publica perfis do plugin por `id`, `name` e `alias`; o método criado continua carregando a configuração declarativa.
4. **Execução:** o núcleo lê o alias da configuração, valida que pertence ao plugin, monta fallback e entrega o alias ativo ao handler.
5. **Preparação/readiness:** `status/prepare` executam o handler com `invocation.mode = configure`; o handler calcula a pasta e grava/lê marker dentro dela.
6. **Continuidade:** conversa reutilizada compara também o perfil configurado para evitar reaproveitar sessão em outro alias.
7. **Exportação:** `connectionId` é retirado, mas a configuração do plugin é copiada; portanto aliases principal/fallback atuais permanecem no Método portátil.
8. **Desinstalação:** todos os registros `plugin_profiles` daquele plugin e o `plugin_workspaces` são removidos; a pasta apontada pelo workspace customizado não é apagada pela rota.

## Decisões derivadas para as próximas fases

- A migração deve criar um `browser_profile` distinto para cada linha legada de `plugin_profiles`; aliases iguais entre plugins não autorizam fusão.
- O resolvedor legado precisa continuar aceitando `pluginId + alias` antes de qualquer troca no editor, MCP ou executor.
- `plugin_workspaces.directory` deve ser tratado como dado potencialmente contendo sessão física; nenhuma migração deve mover a pasta automaticamente.
- Readiness por plugin não pode continuar inferido apenas pelo marker físico comum `.contentflow-profile-ready.json`.
- A fase 4 precisa introduzir `getProfilePath()` sem mudar a semântica de `getWorkspacePath()` para checkpoints/estado privado.
- A fase 6 deve adaptar cada convenção de pasta explicitamente; não existe hoje um único layout que possa ser substituído por busca textual global.

## Fora do escopo do pacote 1.1

Não foram criadas tabelas globais, vínculos, readiness novo, migração, lock/lease, `getProfilePath()`, alterações de sandbox, mudanças de UI, reescrita de Método, adaptação de plugin ou movimentação de pastas. Esses efeitos pertencem às fases posteriores do roadmap.
